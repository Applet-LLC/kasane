# Windows 11 の「管理者保護」（Administrator protection）が kasane に与える影響

2026-10-11 時点の検討メモ。**実機では未検証**（この開発機は管理者保護が無効: `Lsa\TypeOfAdminApproval` が未設定）。
コードで確認できた事実と、Windows 側の仕様についての理解（要実機確認）を分けて書く。

## 1. 管理者保護とは（Windows 側の仕様。要実機確認）

Windows 11 に入った、UAC の昇格方式を変えるオプション機能（既定は無効）。
「UAC: 管理者承認モードの種類」を「管理者保護を使用した管理者承認モード」にすると有効になる。

- 昇格すると、ユーザー自身の管理者トークンではなく、**システムが管理する別の管理者アカウント（SMAA）のトークン**で動く。
  このトークンは昇格のたびに作られ、プロセスが終わると捨てられる（常に有効な管理者トークンが残らない）。
- 昇格のたびに認証（Windows Hello など）が要る。静かな昇格（ConsentPromptBehaviorAdmin による自動承認）は無い。
- 昇格したプロセスは、整合性レベル（IL）は従来どおり High。**UIPI の規則は変わらない**。
- 昇格したプロセスは**別のユーザー**として動くので、HKCU・`%LOCALAPPDATA%`・`%APPDATA%`・`%TEMP%`・ユーザーのドライブ割り当てが、
  元のユーザーのものと**別になる**。

## 2. 前提の整理: LL フックは管理者権限が無くても張れる

「LL Hook は管理者権限が必要」というより、問題は次の点にある。

- `SetWindowsHookEx(WH_KEYBOARD_LL)` は、**通常権限（IL Medium）のプロセスでも張れる**。kasane のトレイも通常権限で張っている
  （`kasane-tray`。`requestedExecutionLevel=asInvoker`）。
- ただし UIPI により、**前面のウィンドウが昇格している（IL High）とき、通常権限のフックにはそのキーが届かない**（`SendInput` も届かない）。
  これは管理者保護の有無と関係なく、従来の UAC でも同じ。
- 管理者保護で変わるのは、**フックの届き方ではなく、「昇格して回避する」という常套手段が使いにくくなること**（第3節）。

kasane のトレイは `uiAccess="true"`（署名済み・`Program Files` 配置が条件）で UIPI を越える設計（`docs/ARCHITECTURE.md` の「uiAccess」）。
`kasane-launcher`・`DriverManager` だけが `requireAdministrator`。

## 3. 一般的なキーリマップソフト（LL フックだけに頼るもの）への影響

- 昇格したウィンドウ（管理者のコマンドプロンプト、タスクマネージャー等）が前面のときは、従来どおりフックにキーが届かず、リマップが効かない。
- 回避策として使われる「ソフト自体を管理者として動かす」「ログオン時にタスクスケジューラで最上位の特権で起動する」は、管理者保護では次の問題が出る（理解。要確認）。
  - 昇格のたびに認証が要る。ログオン時の自動起動は、静かには昇格できない。
  - 昇格した側は別ユーザー（SMAA）で動くので、設定ファイル（`%APPDATA%` 等）が元のユーザーのものと別になり、設定が見つからない・共有できない。
- つまり、LL フック頼みのソフトは、「通常権限では昇格ウィンドウに効かず、昇格して動かすと自動起動と設定の扱いが壊れる」という両面の問題を受ける。

## 4. kasane の機能ごとの影響

| 機能 | 動く場所 | 管理者保護での影響 |
|---|---|---|
| キーのリマップ、レイヤー、タップ/ホールド、コンボ、マクロ、NICOLA | **ドライバ**（カーネル） | **影響なし**。UIPI の下の層で動くので、前面が昇格ウィンドウでも効く。 |
| `HLP(id)` のヘルパーイベント | ドライバ → トレイ（`WAIT_HELPER_EVENT`。`FILE_READ_ACCESS`） | **受け取りは影響なし**（昇格ウィンドウの上でも受けられる）。動作の実行は `SendInput` のため、下の行と同じ。 |
| F13〜F24 などのトリガー（LL フック） | トレイ | uiAccess 版なら昇格ウィンドウの上でも届く。uiAccess が付かない場合（署名・場所・シェル以外の親が起動）は、昇格ウィンドウの前面で届かない。従来と同じ。 |
| `Sequence`（`SendInput`）の注入 | トレイ | 同上。uiAccess 版なら昇格ウィンドウにも届く（UAC のセキュアデスクトップには届かない）。 |
| IME 連動・アプリ別レイヤー | トレイ（WinEvent フック） | 前面の exe パスは `QueryFullProcessImageName` で昇格アプリでも取れる。IME の状態は UIPI で取れず、直前の状態を保つ。従来と同じ。 |
| トレイの一時停止・レイヤーメニュー・緊急解除 | ドライバのコントロールデバイス（`FILE_READ_ACCESS`） | 影響なし。Everyone が読み取りで開ける設計なので、通常権限のまま動く。 |
| エディタの書き込み系操作（適用、キャリブレーション、`CAPTURE_NEXT_KEY` など） | エディタ（昇格） | ドライバのアクセス制御は `BA`（Administrators）なので、昇格したトークンなら通るはず。ただし第5節の問題がある。 |
| インストーラー、`DriverManager`、ライセンスサービス | 昇格 / SYSTEM | インストール時の昇格は従来どおり。`kasane-license-svc` は `CommonApplicationData`（`ProgramData`）を使うので、ユーザーに依存しない。 |

## 5. 最も影響が大きい点: 昇格したエディタの設定の保存先が別になる

エディタは、書き込み系の操作のために「管理者として再起動」（`runas`。`MainWindow.xaml.cs`）で昇格する。

管理者保護が有効だと、昇格したエディタは**別ユーザー（SMAA）**として動く。そのため `Environment.SpecialFolder.LocalApplicationData` が
元のユーザーのものと別になり、次のファイルを**別の場所から読み、別の場所へ書く**ことになる（理解。要実機確認）。

- `%LOCALAPPDATA%\applet\kasane\<UniqId>\project.json`（キーボードごとの設定）
- `%LOCALAPPDATA%\applet\kasane\<UniqId>\helper.json`（ヘルパー動作・アプリ別レイヤー）
- `%LOCALAPPDATA%\applet\kasane\tray.json`（トレイの設定。IME 連動、共通のヘルパー設定）

起きうること:

1. 通常権限のエディタで作った設定が、昇格したエディタに出てこない（設定が消えたように見える）。
2. **昇格したエディタで保存したヘルパー動作・アプリ別レイヤーが、トレイ（元のユーザーで動く）に届かない**。
   トレイは自分の `%LOCALAPPDATA%` を 3 秒ごとに読み直すだけなので、SMAA 側に書かれたファイルは読まない。
3. トレイの起動・終了などを昇格側から操作しても、`Local\kasane-tray` のミューテックスや `tray.log`・`tray-state.json` の場所が、ユーザーごとに別になる。

ドライバに入った設定（レイヤーマップ、レジストリ `HKLM\...\kbdlayer`）は、ユーザーに依存しないので影響を受けない。
影響を受けるのは「ユーザーごとのファイル」だけ。

なお、標準ユーザーが管理者の資格情報で昇格する従来の UAC（別アカウントでの昇格）でも、同じ問題は起きうる。
管理者保護は、これを**管理者アカウントでも一律に**起こす。

## 6. 対策の案（未実装）

優先順に。

1. **エディタの保存先を、昇格しても変わらない場所に寄せる。** 元のユーザーの `%LOCALAPPDATA%` を、昇格前のエディタが引数（または環境変数）で渡し、
   昇格したエディタはそれを使う。あるいは、ユーザーごとのファイルの読み書きを、通常権限のプロセス（トレイ）へ頼む。
   - **環境変数方式（のどかと同様。方針は未決定）**: 保存先を環境変数（例: `KASANE_DATA_DIR`）で決められるようにする。あれば使い、なければ従来の
     `%LOCALAPPDATA%\applet\kasane`。エディタ・トレイ・ライセンス管理が同じ解決処理（`HelperConfig` などに散らばる `LocalApplicationData` の参照を1か所に集約）を使う。
   - 決めること: (a) 環境変数名と優先順位。(b) 既定の場所を `%LOCALAPPDATA%` のままにするか、ユーザーに依存しない場所（`%ProgramData%` 配下など）に変えるか
     （後者は管理者保護でも変わらないが、ユーザーごとの設定という性質と、書き込み権限の設計が変わる）。(c) `runas` で昇格するときの引き継ぎ。
     昇格は別ユーザーで起動するため、環境変数が引き継がれる保証は無い（要確認）。通常権限側が自分の保存先を**起動引数で渡す**方が確実と考えている。
2. **昇格が要る操作を最小にする。** 設定の編集・保存・エクスポートは通常権限のまま行い（現在もそう）、昇格は「ドライバへの適用」のときだけにする。
   昇格する側は、ファイルを自分で読まず、通常権限側が渡した内容（標準入力、名前付きパイプ）だけを使う。
3. 昇格したエディタが開いたとき、保存先が元のユーザーのものでないと検出したら、画面に警告を出す。
4. ドキュメントに、管理者保護を有効にした環境での使い方（昇格したエディタの設定は、トレイに届かない場合がある）を書く。

## 7. 実機で確認すること

1. 管理者保護を有効にした Windows 11 で、`kasane.exe` を通常起動 → 「管理者として再起動」し、`%LOCALAPPDATA%` の指す場所と、`project.json` が読めるか。
2. 昇格したエディタで保存した `helper.json` / `tray.json` が、トレイに反映されるか（`tray.log`）。
3. uiAccess 版トレイが、管理者保護が有効な環境で起動でき、管理者のコマンドプロンプトの前面で F13 トリガー・`SendInput` が届くか。
4. 昇格したエディタから、ドライバの書き込み系 IOCTL（`BA` の許可）が通るか。
5. 一時停止・レイヤーメニュー・`HLP(id)` が、昇格ウィンドウの前面で動くか（ドライバ経路なので、動くはず）。
6. 管理者保護を有効にしたまま、インストーラー（MSI）・アンインストールが通るか。
